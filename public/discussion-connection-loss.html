When a discussion's connection drops

One conversation ended early with a server error in the log. This page records what happened, what the code does when either of a participant's two connections is lost, and what it does not do: there is no retry anywhere. Background on the widget itself is in The discussion widget, end to end.

1. What happened

Two people were talking. About 3 minutes 30 seconds in, during the first one-minute extension (the conversation was due to end at 4:00), it stopped for both:

ParticipantSawWhich means
A"The other participant left the conversation."The server sent over { reason: "left" }. It only does that from left(), when the other socket has closed by itself.
BA connection failure. The exact sentence was not written down; from the code it should have been "The connection was lost."B's WebSocket closed without the server having sent over first. The widget shows this for any such close.

The server log had one line, with the error's own message missing from what was copied:

Closing the SFU tracks failed:
    at Discussions.sfu (index.js:1319:37)
    at async Discussions.silence (index.js:1279:28)
    at async Discussions.left (index.js:1265:3)
    at async Discussions.webSocketClose (index.js:1172:3)
In short

B's WebSocket closed. That is what ended the conversation. The logged error came afterwards, from the clean-up, and did not cause anything either participant saw. Why B's socket closed is not known (section 7).

2. Reading the server log

The stack trace gives the order of events inside the Durable Object:

  1. Browser B
    Its WebSocket closes. Not through dismiss(): the seat is not marked over, so the close is processed.
  2. Object
    webSocketClose(B) calls left(B), which marks B's seat over.
  3. Object
    Fewer than two members remain, so end(id, "left", B): A is sent over { reason: "left" } and its socket is closed, the conversation is deleted from storage, and A's SFU tracks are closed with silence(A.session).
  4. Object
    Back in left(): schedule(), then silence(B.session) for the participant whose socket closed.
  5. SFU
    Refuses the call. sfu() throws, silence() catches it and logs "Closing the SFU tracks failed".

The trace goes left → silence directly, not through end(), so the session the SFU refused was B's own, not A's.

Which HTTP status came back was not captured. Cloudflare's documentation describes one case that fits: a session whose WebRTC connection has been lost can be reused for about 30 seconds, and after that calls on it return HTTP 410 with session_error. If that is what happened, B's audio connection had already been gone for a while when the socket closed, and there was nothing left for silence() to close.

One thing the outcome rules out

A restart of the Durable Object (a deploy, or the dev server reloading the worker) drops every socket at once. Both participants would then have seen "The connection was lost", and no webSocketClose would have run. A was told "left", so the object was alive and saw only B's socket go.

3. Two connections, two failures

Each participant has two separate connections, and they fail separately:

ConnectionCarriesIf it is lost
WebSocket to the Durable ObjectWho is in the conversation, the timer, extension votes, the SDP exchanges.The widget ends at once for that participant ("The connection was lost"). The other is told "left", or gets a new state if a third person remains.
RTCPeerConnection to the SFUThe audio, both directions.The widget carries on, silent, with "The audio couldn't connect." in red. The timer keeps running and the other participant is not told.

A network outage on one side usually takes both, but not at the same moment. The SFU notices missing media within seconds. A WebSocket whose network has vanished can sit open for much longer, until the operating system or an intermediary gives up on the TCP connection. So the audio connection going first and the socket following later is the expected order for a dropped network.

4. What the browser recovers by itself

SituationBrowser, unaided
Short interruption on the same network; the peer connection goes disconnectedKeeps probing the network paths it already has and often returns to connected. No code needed.
Network change (Wi-Fi to mobile, new IP address) or a longer outage; the peer connection goes failedNothing. It stays failed until the page calls restartIce() and a new offer/answer is exchanged.
WebSocket closesNothing. Browsers never reconnect a WebSocket.

5. What our code does

There is no retry logic in the browser code or in the Durable Object.

In app/components/chat/Discussion.tsx

  • Peer connection failed. The connectionstatechange listener sets audioFailed, which shows the red sentence. The flag is never cleared, and nothing is restarted.
  • WebSocket close. The listener calls end("error"): the peer connection is closed, the microphone released, and the widget shows "The connection was lost." No new socket is opened.
  • One publish per mount. publish() is guarded by the publishing flag, so the peer connection is built once and never rebuilt.

In workers/discussions.ts

  • A closed socket is a departure. webSocketClose and webSocketError both go to left(). With two participants that ends the conversation for the other one immediately; there is no grace period in which the first could come back.
  • One publish per seat. seat.publishing is set on the first publish and never reset, so even a client that built a second peer connection would have its offer ignored.
  • One seat per account. A second socket for a user who still has one open is turned away with busy.
  • The cause of a close is discarded. webSocketClose does not log its close code, and webSocketError does not log its error. An abnormal drop leaves no trace on the server.

6. The change that was made

silence() no longer logs when the SFU answers 410: that session is gone and there is nothing to close. Every other failure is still logged. sfu() now throws an SfuError that carries the HTTP status so the caller can tell the cases apart. 

} catch (e) {
  // The SFU let go of the session first: its connection dropped before
  // the socket did, and there is nothing left to close.
  if (e instanceof SfuError && e.status === 410) return;
  console.error("Closing the SFU tracks failed:", e);
}
Limits of this change
  • It only quiets a log line. A dropped connection ends the conversation exactly as before.
  • It rests on the documentation, not on the incident: the status in the original error was not captured. If the line appears again, the status was something else and the full message will say what.
  • It typechecks. It has not been run against the real SFU.

7. What is not known

  • Why B's socket closed. Nothing recorded the close code. A network drop or change, or a machine going to sleep, on B's side would fit, but none of these was observed.
  • Which connection went first. The 410 reading says the audio did, at least 30 seconds earlier. Nobody reported the audio cutting out before the end, and nobody was asked.
  • The status the SFU returned. See section 6.
  • Whether the timing matters. With the end at 4:00, the offer of a second extension appears at 3:30, about when this happened. The extension code (vote(), tally(), the widget's extend button) was read and nothing in it closes a socket, so this is recorded as a coincidence, not a lead.
  • Whether an ordinary "leave" can log the same line. Leaving closes the socket and the peer connection together, so the SFU may already consider the session closed when silence() asks about it. Not tested.

Logging the close code in webSocketClose and the error in webSocketError would answer the first two the next time it happens. That has not been added.

About this file
