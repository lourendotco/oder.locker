End-to-end encryption and reporting for discussions

Two proposals for the voice widget and how they fit together: encrypting the audio so that neither Cloudflare nor our own server can hear it, and letting a participant report another with a recording made on their own device.

Short answers
  • Can we do end-to-end encryption? Yes. The media part is small. The hard part is agreeing on keys in a way the server cannot interfere with, and that part can only be made partly trustworthy in a web app.
  • Do we need audio workers for performance? Not for performance. Encrypting voice is about 50 tiny frames a second, which is nothing. But the standard browser API for this runs in a Web Worker by design, so there will be one anyway. An AudioWorklet is the wrong tool and is not needed.
  • Does local recording for reports work? Technically yes, it is cheap, and it is the one moderation approach that still works with end-to-end encryption. Its two real problems are not technical: recording someone's voice without consent is a criminal offence in Germany, and a recording uploaded by a user is not proof.
  • What I would build first: reporting with a pairwise block (sections 8 to 12), then encryption.

Part one · encryption

1. Where we are today

Audio is encrypted between each browser and Cloudflare's SFU (DTLS-SRTP, automatic). Inside the SFU it is decrypted and re-encrypted for each listener. So the audio is protected from the network, but Cloudflare is technically able to access it. Our own worker never sees audio, only connection setup text.

End-to-end encryption (E2EE) adds a second layer: the browser encrypts each audio frame with a key only the participants hold, before WebRTC's own encryption. The SFU still unwraps the outer layer and forwards the frame, but what it forwards is ciphertext.

2. What E2EE would and would not protect

AgainstProtected?Why
Someone on the networkAlreadyDTLS-SRTP does this today.
Cloudflare's SFU reading or recording audioYesIt only ever handles ciphertext.
Our server, if it only watches (logs, a leak, a subpoena for stored data)YesWith keys agreed between browsers (section 5), nothing the server relays is enough to decrypt.
Our server, if it actively cheats during key exchangeOnly with verificationThe server relays the public keys and could swap them for its own. Participants would have to compare a short code out loud to detect it.
Us shipping different JavaScriptNoThe page that does the encrypting is served by us. A changed script could send the key anywhere. Every web-based E2EE system has this limit; apps installed from a store have it less.
The other participant recording the callNoThey hear it, so they can record it. No encryption changes that.
Metadata: who talked to whom, when, for how longNoThe Durable Object needs all of that to run the conversation.

The honest claim we could make afterwards is: "audio is end-to-end encrypted between participants; our servers and Cloudflare relay it but cannot hear it." Not: "nobody could ever listen." The gap between those two is the last two No rows above.

3. Encrypting the audio frames

Browsers expose a hook between the audio encoder and the network, called WebRTC Encoded Transform. On the sending side our code receives each encoded Opus frame (about 20 ms of sound, typically 60 to 120 bytes) and may replace its bytes. On the receiving side it gets the frame before the decoder.

The API, in two flavours

  • Standard: RTCRtpScriptTransform. You create a Worker and attach it: 
    const worker = new Worker(new URL("./e2ee.worker.ts", import.meta.url), { type: "module" });
sender.transform = new RTCRtpScriptTransform(worker, { side: "send" });
receiver.transform = new RTCRtpScriptTransform(worker, { side: "receive", from: userId });
    Inside the worker an rtctransform event hands over a readable and a writable stream of frames. Supported in Safari and Firefox, and in recent Chrome.
  • Legacy Chrome: sender.createEncodedStreams(), with encodedInsertableStreams: true in the peer connection's configuration. Needed only if we want to support Chrome versions from before it shipped the standard API.

Exact version numbers should be checked on MDN or caniuse at the time of building. A browser with neither API must be refused a place in an encrypted conversation, not silently let in unencrypted.

What the transform does

// sending, per frame
const counter = next++;                       // never reused with the same key
const iv = makeIv(counter);                   // 12 bytes
const sealed = await crypto.subtle.encrypt(
  { name: "AES-GCM", iv, tagLength: 32 },     // short tag: see below
  key, frame.data);
frame.data = concat(sealed, header(keyId, counter));
controller.enqueue(frame);

The receiver reads the header, finds the key for that sender and key id, decrypts, and passes the frame on. A frame that fails to decrypt is dropped, which sounds like a tiny gap.

  • Format. There is a standard for exactly this: SFrame (RFC 9605). It defines the header (key id and counter) and the cipher suites. Following it is better than inventing a layout, even if we write the few dozen lines ourselves.
  • Overhead. Every frame grows by the authentication tag plus a few header bytes, 50 times a second. With a full 16-byte tag that is around 8 kbit/s on top of a voice stream of perhaps 30, which is a lot. SFrame's audio suites use short tags (4 bytes) for this reason; the trade-off is a weaker guarantee against forged frames, which for live voice is acceptable.
  • Counters. AES-GCM breaks badly if a key is ever used twice with the same counter. Each sender has its own key, so a counter that starts at zero when the key is created and only goes up is enough.
  • Mute. A muted microphone still produces (silent) frames, which get encrypted like any other. Nothing special.

4. Workers and performance

Three different things get called "audio workers", and they have different answers.

ThingWhat it is forDo we need it?
Web WorkerRunning JavaScript off the main thread.Yes, for E2EE, because RTCRtpScriptTransform only runs in one. Not because the work is heavy.
AudioWorkletProcessing raw, uncompressed sound samples in real time (effects, analysis, custom codecs).No. We never touch raw samples. Encryption happens on compressed frames, after the encoder.
Worker for recording—No. MediaRecorder (part two) is implemented natively by the browser and already runs off the main thread.

On cost: 50 frames per second, each around a hundred bytes, with hardware-accelerated AES. That is microseconds of work per frame, for each of at most three streams. The reason the API insists on a worker is jitter, not throughput: if the main thread is busy for 200 ms rendering the feed or typing out a chat bubble, frames handled there would be late and the audio would crackle. In a worker they are not affected.

One practical note for this project: the worker is a separate bundle. Vite handles new Worker(new URL(…, import.meta.url)) out of the box, and it must only be created in the browser (inside the existing effect in Discussion.tsx), never during server rendering.

5. Agreeing on keys

This is where the real design decisions are. Three options, from weakest to strongest.

Option A: the server hands out a key

The Durable Object generates a random key per conversation and sends it over the WebSocket. Very easy. It hides the audio from the SFU, but our own server holds the key, so it is not end-to-end encryption and must not be called that. Since the SFU and the worker are both Cloudflare services, it barely changes who could listen. Not recommended.

Option B: the browsers agree between themselves, the server only relays

  1. Each browser creates a throwaway ECDH key pair when the conversation starts (crypto.subtle.generateKey, curve P-256 or X25519) and sends the public half to the others through the Durable Object.
  2. Each pair of participants derives a shared secret from their own private key and the other's public key (deriveBits, then HKDF). The server sees only public keys, which are not enough.
  3. Each participant creates a random sender key for their own audio, and sends it to each other participant encrypted under the pairwise secret.
  4. Everyone now holds one key per speaker. Frames are encrypted with the speaker's sender key.

"Sender keys" is what makes three people work: each stream is encrypted once and all listeners can read it, instead of encrypting separately per listener.

When membership changes (the third person joins within 30 seconds, or someone leaves), everyone makes a fresh sender key and distributes it again. This way a late joiner cannot decrypt what was said before they arrived, and someone who left cannot decrypt what follows.

What it achieves: a server that only observes learns nothing. What it does not: a server that actively swaps public keys in step 1 can sit in the middle unnoticed.

Option C: B, plus a way to check

Both browsers compute a short code from the public keys they saw (say four digits or three emoji) and display it. If the participants read it to each other and it matches, nobody swapped keys. This is what Signal's safety numbers and Matrix's emoji verification do.

It fits oddly here: these are strangers with three minutes and a list of questions to get through. A small, optional "security code: 4 7 1 9" in the widget costs nothing and lets anyone who cares check. A mandatory step would eat the conversation.

Recommendation

Option B with the optional code from C. Larger protocols built for this (MLS, RFC 9420) solve problems we do not have: big groups, long-lived sessions, members on several devices. For two or three people and ten minutes, pairwise ECDH with sender keys is the appropriate size.

6. What would change in our code

FileChange
app/lib/discussion.tsOne new message in each direction, key { to, payload } / key { from, payload }. The payload is opaque to the server.
workers/discussions.tsRelay key messages to the named participant, only within the same conversation, with a size cap. Nothing else: the server gains no knowledge.
app/lib/e2ee.worker.ts (new)The transform: holds the keys, encrypts outgoing frames, decrypts incoming ones.
app/lib/e2ee.ts (new)Key pairs, derivation, sender keys, the verification code. Runs on the main thread and posts keys to the worker.
Discussion.tsxCreate the worker; attach the transform to the sender in publish() and to each receiver in the track handler; exchange keys when state shows a membership change; show a lock and the code; refuse to start if the browser lacks the API.

The SFU calls, the matching, the timers and the abuse limits stay exactly as they are. The SFU does not need to be told anything.

One ordering detail matters: keys must be in place before audio is unmuted to the user. Until a listener has the speaker's key, frames are dropped. That is safe (silence, not noise), but the widget should show "securing…" for the moment it takes.

7. Risks and unknowns

  • Unconfirmed: does Cloudflare's SFU forward frames it cannot parse? For audio it should, since an SFU forwards packets without decoding them, and Cloudflare's documentation does not mention end-to-end encryption either way. This needs a half-day experiment before committing: encrypt on one side, decrypt on the other, through the real SFU.
  • Three browser engines. The transform API is where Chrome, Safari and Firefox differ most in WebRTC. Expect most of the effort to go into testing on real phones, not into the cryptography.
  • Debugging gets harder. "No audio" gains a new cause (keys out of step) that looks identical to the network ones.
  • Server-side features become impossible. Anything that needs the server to hear the audio stops working: server-side recording, transcription, automatic moderation. Cloudflare's WebSocket adapter (section 11) decodes Opus on Cloudflare's side and would receive garbage.
  • Custom cryptography. Even assembled from standard parts, the key exchange is security-critical code written by us. It deserves a review by someone who does this for a living before the word "end-to-end" goes on the site.
Part two · reporting

8. Reporting: the idea

Your proposal: every participant's browser records the conversation locally from the moment it starts. If nobody reports, the recording is thrown away and never leaves the device. If someone clicks Report, their browser uploads it, and you can listen and block the offender.

This is a sound design and a well-known one: it is how reporting works in end-to-end encrypted messengers, where the server has nothing to look at and a report is one participant voluntarily disclosing what they received. Its strengths are that nothing is stored unless there is a complaint, and that it captures what happened before the click, which is the part that matters.

9. How local recording would work

In the browser

  • MediaRecorder records a MediaStream to compressed audio. We already hold the streams: one per remote participant (the voices state) and the user's own microphone.
  • One recorder per participant, not a mix. In a three-person call a single mixed recording cannot tell you who said what, and you need to block the right person. Separate files, each labelled with a user id, can. Recording the reporter's own microphone too gives context ("what was that a reply to?").
  • Format. Chrome and Firefox produce audio/webm with Opus; Safari produces audio/mp4. Use MediaRecorder.isTypeSupported and store the type with the file.
  • Size. Ask for a low bitrate (audioBitsPerSecond: 24000). Ten minutes is then under 2 MB per participant, held in memory as chunks. No IndexedDB, no worker.
  • Lifetime. Start when the first audio arrives; stop when the widget is over. Keep the chunks for a few minutes afterwards so "report" still works from the "conversation has ended" state, then drop them. Reloading the page loses them, which is acceptable.
const recorder = new MediaRecorder(voice, { audioBitsPerSecond: 24_000 });
const chunks: Blob[] = [];
recorder.ondataavailable = ({ data }) => chunks.push(data);
recorder.start(5_000);            // a chunk every 5 s, so little is lost on a crash
// on report:
const file = new Blob(chunks, { type: recorder.mimeType });

On the server

  • An upload route (a normal React Router action, like the profile picture upload): signed-in users only, a hard size limit checked on Content-Length before reading the body (the pattern already in home.tsx), and a rate limit on reports per account.
  • A membership check. The server must confirm the reporter and the reported person really were in a conversation together, recently. Today the Durable Object deletes a conversation the moment it ends, so it would need to keep a small record (conversation id, member ids, start and end) for a day or so.
  • Storage. A separate, private R2 bucket. The existing PHOTOS bucket is served publicly through media.oder.locker and must not be used. A reports table in D1: reporter, reported, conversation, time, file keys, a reason, status, decision.
  • Retention. Delete the audio when the report is decided, or after a fixed period (say 30 days), whichever comes first. The daily cron that already purges tokens can do it.
  • A place to review. Someone has to listen. That means a small admin page, and deciding who has access to it.

10. Consent and the law

This needs a lawyer before it ships

I am not one, and this section is a list of things to ask about, not advice. But they are serious enough to shape the design.

  • Recording itself. In Germany, recording another person's non-public spoken words without authorisation is a criminal offence (§ 201 StGB, Verletzung der Vertraulichkeit des Wortes), and so is making such a recording available to a third party. A private conversation between two users is not public. "It only stays on the device unless reported" does not obviously help, because the recording is what is prohibited. The usual way to be authorised is consent from everyone recorded.
  • What is being said. The whole point of the widget is to discuss a political question. Recordings will therefore routinely reveal political opinions, which the GDPR treats as a special category of personal data (Art. 9) with stricter conditions. A voice is also personal data in itself.
  • Who is responsible. Our code makes the recording, so we cannot treat it as something users do on their own.

What follows for the design, whatever the legal detail turns out to be:

  • Tell people before they join, and make them agree. A clear line on the widget before searching starts: the conversation is recorded on each participant's device, and a participant can send it to the moderators with a report. Starting means consenting. No dark pattern, no pre-ticked box.
  • Show it while it happens. A visible recording indicator for the whole conversation.
  • Update the privacy page (app/routes/privacy.tsx): what is recorded, where it is stored, for how long, who can hear it, and how to ask for deletion.
  • Keep the minimum. Upload only on report, restrict access, delete on a schedule.
  • Consider a shorter window. Keeping only the last two minutes in memory instead of everything reduces what can leak, at the price of missing earlier context. Worth raising with whoever advises you.

11. Can a recording be trusted?

The upload comes from the reporter's device, and the reporter controls that device. They can cut the recording, splice it, or replace it with something else entirely, including a cloned voice. So a report is a claim with supporting material, not proof, and blocking must not be automatic.

What the server can know for certain, and should check:

  • These two accounts were in the same conversation, at this time, for this long.
  • The recording's length is plausible for that conversation.
  • How many reports this account has filed, and how many have been filed against the other, by how many different people.

That last point is the strongest signal available. One report is an accusation. Five reports from five unrelated accounts is a pattern, whatever any single recording contains.

The alternative: recording on the server

Cloudflare's SFU has a "WebSocket adapter" (in beta) that streams a track's audio to a backend as raw PCM. The Durable Object could start one when a participant presses report.

Recording everything on the server is the most reliable evidence and the worst for privacy; it is hard to justify for a discussion of political opinions. Capturing only after the click misses the offence. Local recording is the best fit, as long as reports are treated as claims.

A cryptographic fix for the trust problem exists in theory (each speaker signs their audio, so a recording can be checked against the speaker's key) but it is impractical: signatures would have to cover the compressed frames, the reporter would have to upload those instead of a playable file, and it adds per frame cost. Not worth it at this scale.

12. Blocking

Two different tools, and the first needs no review at all.

Pairwise block: "never match me with them again"

  • Applied instantly when someone reports, or offered on its own as "don't match us again" with no accusation attached.
  • A blocks table in D1 (blocker, blocked). The worker loads the user's list when the WebSocket opens and passes it to the Durable Object alongside x-user; matching skips those pairs in both directions.
  • Cannot be abused to harm anyone: the worst a false block does is keep two people apart.
  • Reporting should also end the conversation for the reporter immediately.

Ban: "this account may not use discussions"

  • Set by you after reviewing reports. A column on users, checked in discuss() in workers/app.ts before the upgrade is forwarded.
  • Should never be triggered by a single report automatically, for the reasons in section 11.
The weak point: guest accounts

Anyone can sign in as guest_<word> with no email. A banned guest picks a new word and is back in seconds, so a ban only means something for accounts tied to an email address. The simplest fix is to allow voice discussions only for email-verified accounts. Banning by IP address is the other route, and it is both unreliable (shared and mobile addresses) and a privacy cost of its own.

Together

13. How the two fit together

  • They are compatible. Recording happens in the browser after decryption, on the same streams that are played. Encryption does not get in its way.
  • Local reporting is what makes E2EE affordable. Once the server cannot hear anything, participant reports are the only moderation possible. Building reporting first means encryption does not remove a safety net.
  • Be precise in what we tell users. "End-to-end encrypted" and "the other person can send a recording to moderators" are both true at once, and both must be said. Encryption protects the conversation from outsiders, not from the people in it.
  • A reported recording is no longer end-to-end protected. Once uploaded it is ordinary data on our server and has to be guarded as such.

14. Suggested order

  1. Pairwise block and a "don't match us again" button. Small, no legal questions, immediately useful.
  2. Restrict voice to email-verified accounts, so that any later ban has teeth.
  3. Get advice on recording and consent. The answer decides whether step 4 looks like this document or needs to change.
  4. Reporting with local recording: consent line, indicator, recorders, upload route, private bucket, reports table, retention, a review page, the ban flag.
  5. A half-day experiment to confirm encrypted frames pass through Cloudflare's SFU on Chrome, Safari and Firefox.
  6. End-to-end encryption with pairwise ECDH, sender keys and the optional verification code, followed by an outside review before it is advertised.

Steps 1 and 2 address harm that can happen today. Step 6 protects against a threat (Cloudflare or our own server listening) that is real but much less likely than one user being unpleasant to another, which is why it comes last.
