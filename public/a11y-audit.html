Executive summary

The application is in better shape than most at this stage. Accessibility has clearly been considered while writing it: there is a skip link, real landmarks, one <h1> per page, labelled form fields, a native modal <dialog>, language markup on German quotations, a reduced-motion fallback for every CSS animation, and deliberate focus management after client-side navigation.

No critical (blocking) issue was confirmed from the source. Three high-severity issues were:

  1. The two brand colours fail text contrast. White on the purple measures 3.86:1 and white on the orange 3.05:1, against a required 4.5:1. This affects every form field, every primary button, the sign-in headings and the conversation timer.
  2. The desktop “phone frame” shrinks when the window is short or zoomed. Above 640 px wide the frame's width is derived from the window height, so at 200% zoom on a 1280×720 window it works out to about 180 px, narrower than the 320 px form fields inside it.
  3. A screen-reader user is not told when a voice conversation starts. The “looking for someone” status is replaced by the live conversation view, which has no live region, so the participant's name, the timer and the suggested questions arrive silently.
  • 0Critical
  • 3High
  • 10Medium
  • 12Low

On route changes: the app runs React Router 8.4.0 in framework mode with server rendering. React Router itself does nothing for focus or announcements, but the app adds its own handling in Shell.tsx, which moves focus to <main> whenever the pathname changes. Page titles are set per route, but nothing announces them: there is no route announcer and no aria-live region tied to navigation. What a screen reader actually says when focus lands on the unnamed <main> varies by product and requires manual verification. Details are in Route-change accessibility.

How to read this report

Every finding carries one of two evidence labels:

  • Confirmed in source The defect is visible in the code itself (a missing attribute, a computed colour ratio, a code path that never moves focus). No runtime result is implied.
  • Requires manual verification The code suggests a problem, but whether users are affected depends on browser, assistive technology or layout behaviour that cannot be established by reading.

Some findings carry both: the code fact is confirmed, its effect on users is not. Line numbers refer to the working tree on the audit date.

Route-change accessibility

Direct answers

1. Which React Router version and routing architecture?

React Router 8.4.0, framework mode, server-side rendered on Cloudflare Workers.

  • package.json:22 declares "react-router": "^8.4.0"; the installed package is exactly 8.4.0, as is @react-router/dev. React is 19.3.0 installed (^19.2.8 declared).
  • Framework mode: the reactRouter() Vite plugin (vite.config.ts:10), a route config file (app/routes.ts), route modules exporting loader, action, meta and links.
  • react-router.config.ts:6 sets ssr: true. No future flags are set.
  • The server is a Worker calling createRequestHandler (workers/app.ts:7-10).
  • There is no app/entry.client.tsx, so the framework default is used: hydrateRoot(document, <HydratedRouter />) inside startTransition and StrictMode.

Route tree (app/routes.ts:8-16):

  • root.tsx: the HTML document; its component is a bare <Outlet /> (root.tsx:36-38)
    • routes/layout.tsx: a pathless layout that renders <Shell><Outlet /></Shell> (layout.tsx:37-41)
      • / → home.tsx (sign-in, three steps)
      • /theme → theme.tsx
      • /profile → profile.tsx
      • /weeks → weeks.tsx
      • /privacy → privacy.tsx
    • /logout → logout.tsx: action only, outside the layout, no component

Nesting is one level deep. Every visible page is a leaf under the same layout, so Shell, the header and <main> stay mounted across navigations and only the content of the inner <Outlet> is swapped.

2. What does React Router do by default when the rendered <Outlet> changes?

It swaps the element, updates the document head, and resets window scroll. It does not touch focus and announces nothing.

Read from the installed 8.4.0 build in node_modules/react-router/dist/development:

  • Rendering. Outlet just returns useOutlet() (lib/components.js:466-468): the old route element unmounts and the new one mounts. Router state updates are wrapped in React.startTransition (lib/components.js:147, 387).
  • Title. <Meta /> re-runs the matched routes' meta functions and renders a new <title> element (lib/dom/ssr/components.js:347 onwards). The title changes; nothing reads it out.
  • Scroll. <ScrollRestoration /> restores a saved position on back/forward, scrolls to a matching hash target, or otherwise calls window.scrollTo(0, 0) (lib/dom/lib.js:1111-1129).
  • Focus. A search of both the development and production builds finds no call to .focus() and no read of document.activeElement. Focus is left wherever the browser leaves it: on the followed link if it still exists, otherwise on <body>.
  • Announcements. The same search finds no aria-live, no role="status" and no assignment to document.title. React Router 8.4.0 ships no route announcer.

View transitions are opt-in per navigation (the viewTransition prop or option). This app never passes it; its slide animation comes from React's own <ViewTransition> in PageTransition.tsx.

3. Does this application deliberately move focus after navigation?

Yes. Shell.tsx:14-20 focuses <main> when the pathname changes.

The effect compares the current pathname from useLocation() with the previous one. When they differ, and focus is not already inside <main>, it calls main.focus({ preventScroll: true }). <main> has tabIndex={-1} and outline-none (Shell.tsx:48-53). The code comment states the intent: do not leave focus on the followed link or nowhere, and do not steal it from a page that used autoFocus.

What follows from the code:

  • It covers link clicks, back/forward, and redirects that end on a different pathname, including the sign-in redirect to /theme.
  • It is keyed on pathname only. A change of search string alone does not move focus. That is reasonable here, since ?next= is the only query parameter in use.
  • It does not run on full document loads: first visit, and sign-out, which uses redirectDocument (logout.tsx:10). The browser's own page-load behaviour applies there, which is correct.
  • It does not run when the root ErrorBoundary takes over, because that renders a second, freshly mounted Shell whose “previous pathname” starts equal to the current one (finding L5).
  • It does not cover step changes inside / (email → code → sign-up), which happen without a URL change. The code and sign-up steps handle this with autoFocus; going back to the email step does not (finding M2).
  • <main> has no accessible name, and no visible focus indicator when focused this way (finding M1).

Requires manual verification Whether the effect fires at the right moment relative to the view transition, and what each screen reader says when focus lands on <main>.

4. Are route changes or title changes announced through an aria-live region?

No.

Every live region in the application was located. None relates to navigation:

  • theme.tsx:250 and theme.tsx:385: aria-live="polite" around chat content.
  • ChatBubble.tsx:200: aria-live="off" on the emoji picker.
  • home.tsx:291, 326, 369, 475: role="alert" for form errors; home.tsx:375: role="status" for “requested a new code”.
  • Discussion.tsx:305, 345, 416: role="status"; :332: role="alert"; :324: role="timer".

The Shell component and both layout files contain no live region, and the framework supplies none. The only signal a screen-reader user gets on navigation is whatever their screen reader says when focus moves to <main>.

High 3 findings

H1Brand colours fail text contrast on fields, buttons, headings and the timer

HighConfirmed in source

WCAG
1.4.3 Contrast (Minimum), AA
Affected
/ (all three steps), /theme voices dialog, Discussion widget
Evidence

Tokens: --color-primary: #f7661e, --color-secondary: rgb(148, 102, 242) (app.css:7-8). None of the text below is “large” in WCAG terms (18 px at weight 500 is not), so 4.5:1 applies.

  • home.tsx:144 field text: white on secondary, 3.86:1.
  • home.tsx:144 placeholder: white/70 on secondary, 2.69:1. The placeholder is the only visible label (see M3).
  • home.tsx:146 submit buttons: white on primary, 3.05:1; on hover (bg-primary/85) about 2.67:1.
  • home.tsx:250, 345, 444 step headings: secondary on neutral-100, 3.54:1.
  • Discussion.tsx:325 timer: secondary on white 3.86:1, switching to primary on white 3.05:1 for the last 30 seconds.
  • Discussion.tsx:369 “Extend”: 14 px white on primary, 3.05:1.
  • theme.tsx:511, 522 “Discuss with another user”: 14 px white on primary, 3.05:1.
User impact
People with low vision or reduced contrast sensitivity, and anyone on a phone in daylight, will struggle to read what they typed into the sign-in fields, the button labels and the countdown. The timer is hardest to read exactly when it matters most.
Recommended fix

Add darker “on-colour” variants and use them wherever the colour carries text or sits behind white text. For example, #7443e0 gives 5.80:1 with white and 5.32:1 on neutral-100; #b93f0b gives 5.56:1 and 5.10:1. Keep the current brighter values for the logo and decoration. Either raise the placeholder to full white or stop relying on it as the label.

Manual verification
Check each listed element with a contrast picker in the browser, including hover and disabled states. Confirm the rendered font weight and size match the classes.

H2Desktop phone frame takes its width from the window height, so it collapses under zoom

HighConfirmed in sourceRequires manual verification

WCAG
1.4.4 Resize Text, AA; 1.4.10 Reflow, AA
Affected
Every route, at viewport widths of 640 px and above (Shell)
Evidence
  • Shell.tsx:23: from the sm breakpoint the outer box is h-screen with py-5.
  • Shell.tsx:33: the frame is h-full sm:aspect-9/16 sm:w-auto max-w-sm. Its width is therefore (viewport height − 40 px) × 9/16, capped at 384 px.
  • Shell.tsx:34: the inner scroller is sm:overflow-auto sm:scrollbar-none: it scrolls in both directions with scrollbars hidden.
  • home.tsx:144, 146, 151: fields, buttons and messages are a fixed w-80 (320 px).

Worked from those classes: a 1280×720 window at 200% zoom is 640×360 CSS px, which still matches sm, giving a frame about 180 px wide. A 1366×768 window at 150% gives about 265 px. A phone in landscape (for example 844×390) gives about 197 px. In each case the content is wider than the frame.

User impact
People who zoom on a laptop get a narrower page the more they zoom, the opposite of what zoom is for. Content is cut off or needs two-dimensional scrolling inside a region with no visible scrollbar.
Recommended fix
Only apply the framed layout when there is room for it, for example with a combined query such as @media (min-width: 40rem) and (min-height: 44rem), and fall back to the full-width mobile layout otherwise. Give the frame a min-width of 20 rem, and replace w-80 with w-full max-w-80.
Manual verification
At 1280×720 and 1366×768, zoom to 150%, 200% and 400% on / and /theme. Rotate a phone to landscape. Look for clipped fields and horizontal scrolling. The widths above are derived from the CSS, not measured.

H3The start of a voice conversation is not announced

HighConfirmed in sourceRequires manual verification

WCAG
4.1.3 Status Messages, AA
Affected
/theme, Discussion widget
Evidence
  • Discussion.tsx:416: the microphone and searching states sit in a role="status" container.
  • Discussion.tsx:308-309: when a match arrives, that container is unmounted and replaced by a plain <div> with the participants, timer and questions. Nothing in it is a live region except the conditional extend prompt and audio error.
  • Discussion.tsx:121-125: if focus was on “stop looking”, it is returned to the <section aria-label="Discussion">, whose name does not change.
User impact
A blind user who starts a search hears “Looking for someone to discuss with…”, then a stranger's voice with no introduction. They are not told who joined, that a three-minute timer is running, or that there are suggested questions.
Recommended fix
Keep one status element mounted for the widget's whole life and write each transition into it: “Connected with Louise. Three minutes. Suggested questions follow.” The same element can carry the end-of-conversation message and the extend prompt (see M5).
Manual verification
With two accounts and a screen reader running on one, start a discussion on both. Note exactly what is spoken at the moment of connection, and whether the participant's name can be found afterwards without sight.

Medium 10 findings

M1After navigation, focus lands on an unnamed <main> and the new page is not announced

MediumConfirmed in sourceRequires manual verification

WCAG
4.1.3 Status Messages, AA (by analogy; a full page change is a change of context); supports 2.4.3 Focus Order, A. 2.4.2 Page Titled is met.
Affected
All client-side navigations (Shell)
Evidence
  • Shell.tsx:14-20: focus is moved to <main> on pathname change.
  • Shell.tsx:48-53: <main id="main" tabIndex={-1} className="… outline-none">, with no aria-label or aria-labelledby.
  • No live region for navigation exists anywhere (see question 4).
User impact
A screen-reader user is likely to hear only “main” after following a link, with no page name. Screen readers differ here, and some may begin reading content. Sighted keyboard users get no visible sign of where focus went, though the page change itself is obvious.
Recommended fix
Either of these, both small:
  • Give each page's <h1> a shared id and set aria-labelledby on <main>, so focusing it speaks the heading; or
  • Focus the <h1> itself (tabIndex={-1}) instead of <main>.
Optionally add a visually hidden role="status" element in Shell that receives document.title after each navigation.
Manual verification
With VoiceOver (Safari), NVDA (Firefox and Chrome) and TalkBack, follow each header link and note the exact speech. Repeat with the browser's back button.

M2Focus is lost when a button removes itself during sign-in

MediumConfirmed in source

WCAG
2.4.3 Focus Order, A
Affected
/, code step and sign-up step
Evidence
  • home.tsx:415-425 “use another email”: the click switches to the email form, unmounting the button. The email input (home.tsx:451-468) has no autoFocus, and the Shell effect does not run because the pathname is unchanged.

M3Placeholders are the only visible field labels

MediumConfirmed in source

WCAG

Affected
/, all steps
Evidence
home.tsx:295-297, 313-315, 350-352, 448-450: every <label> is sr-only. The visible cue is the placeholder (home.tsx:308, 322, 363, 461), which disappears on input. The sign-up step has two adjacent fields, “username” and “name (optional)”.

M5Status messages are inserted together with their live region, and repeated errors are silent

MediumConfirmed in sourceRequires manual verification

WCAG
4.1.3 Status Messages, AA
Affected
Discussion widget; /
Evidence
  • Discussion.tsx:304-307: the end message (“The connection was lost.”, “The other participant left…”) is a role="status" paragraph created at the moment it has content.
  • Discussion.tsx:343-346: the extend prompt is likewise a new role="status" element. It appears 30 seconds before the end and needs a decision.
  • home.tsx:368-372, 474-478: an error paragraph stays mounted with identical text when the same error is returned twice (for example two wrong codes), so the DOM does not change.
User impact
Polite live regions that are added to the page already filled are announced inconsistently across browser and screen-reader pairs. Manual verification
With a screen reader: submit a wrong code twice; let a search time out; have the other participant leave; wait for the extend prompt. Record what is spoken each time.

Affected

The chat-bubble pop-in specifically

This code changed during the audit. When the review began, .bubble-pop-in was defined but applied to nothing. Uncommitted edits to app/app.css and ChatBubble.tsx that appeared partway through wire it up. What follows describes the working tree as it stood when the report was finished.

Confirmed in source Every bubble's shadow wrapper now carries bubble-pop-in (ChatBubble.tsx:93). The rule (app.css:216-237) runs the bubble-scale-in keyframes (app.css:239-243) for 280 ms: the bubble grows from scale 0 out of its bottom-left corner, reaches full size at roughly 150 ms, overshoots by 1% and settles.

Under prefers-reduced-motion: reduce, the rule at app.css:285-290 swaps the keyframes for bubble-fade-in (app.css:279-283). The bubble then fades from transparent over the same 280 ms and does not scale or move. That is the right treatment: the motion is removed and the cue that something appeared is kept. The easing curve's 1% overshoot has no visible effect on opacity.

Points worth knowing:

  • The class is on the wrapper, which stays mounted when a bubble goes from typing dots to text, so the animation plays once per bubble and not again when the text arrives.
  • It plays for every bubble present at first paint as well (the photograph and the opening question), not only for bubbles added later.
  • The animation is short, plays once and involves no flashing. It raises no WCAG AA concern with motion enabled; 2.3.3 Animation from Interactions is AAA and is met anyway through the fallback.
  • The reactions pill animates separately through the Web Animations API and chooses its reduced-motion variant in script (ChatBubble.tsx:64-71). The .pop-in class on the “Add a voice” button and the extend prompt shares the same CSS fallback.

Requires manual verification That the fade is what actually renders with the operating system's reduce-motion setting on, in Safari, Chrome and Firefox, and that the first-paint animation does not replay after hydration.

Not gated, and why that is probably fine

  • active:scale-95 press feedback on buttons (Discussion.tsx:84, 369; theme.tsx:304, 447; ChatBubble.tsx:114): tiny, and user-initiated.
  • The search progress bar (Discussion.tsx:440): a linear width change that conveys progress.
  • Lightbox backdrop and caption fades (app.css:56-84): opacity only. The lightbox library has its own reduced-motion check.

Requires manual verification The search rings and typing dots run indefinitely while their state lasts (up to 60 seconds for the rings). WCAG 2.2.2 expects a way to pause motion lasting over five seconds; “stop looking” ends it, at the cost of ending the search. Also confirm that the header's own view-transition group shows no visible cross-fade with reduced motion on.

Structure and navigation

  • <html lang="en"> and a viewport meta that does not disable zoom (root.tsx:20, 23).
  • A skip link as the first focusable element, visible on focus, that focuses <main> rather than changing the URL fragment the sign-in page reads (Shell.tsx:35-46).
  • Banner, labelled navigation and main landmarks on every page, including the error page (Header.tsx:35, 39; Shell.tsx:48; root.tsx:57).
  • Exactly one <h1> per page and no skipped heading levels.
  • A distinct title for every page route, and for 404 and error states.
  • Deliberate focus movement after client-side navigation that respects autoFocus (Shell.tsx:14-20).

Names and images

  • Icon-only links and buttons have accessible names, with their icons hidden (Header.tsx:42-58; theme.tsx:300, 443, 481; Discussion.tsx:381, 398).
  • Decorative images use alt="" where the name is adjacent; the topic photograph has a full description, repeated in the lightbox (theme.tsx:27-28, 372, 580).
  • The mute button keeps a stable name and exposes its state with aria-pressed (Discussion.tsx:379-382).
  • New-tab links say so in visually hidden text, including “PDF” (ChatBubble.tsx:189-191; privacy.tsx:30).
  • A hidden “Location:” label where only an icon gave the meaning (profile.tsx:46).

Forms

  • Every input has a programmatic label; each form is named by its heading (home.tsx:234, 339, 439).
  • Correct autocomplete tokens: email, one-time-code, username, name; a numeric keypad for the code.
  • Errors use role="alert" and are tied to their field with aria-describedby; the neutral “requested a new code” uses role="status".
  • The error colour was chosen for contrast and measures 5.89:1.
  • Optional fields are marked as optional in their labels.

Dialogs and dynamic content

  • The voices picker is a native modal <dialog> opened with showModal(), labelled by its heading, with a named close button and backdrop dismissal (theme.tsx:455-486). Focus trapping, Esc and focus return come from the browser.
  • The emoji picker closes on Esc and returns focus to its trigger, which exposes aria-expanded (ChatBubble.tsx:111-112, 203-207).
  • Typing indicators carry real text (“… is typing…”) with the dots hidden (ChatBubble.tsx:131-146).
  • The discussion widget takes focus when it appears and keeps it when its buttons disappear (Discussion.tsx:114-125, 367).
  • The countdown is a role="timer" with a hidden “Time left:” prefix, so it does not chatter (Discussion.tsx:323-329).
  • Inactive, not-yet-revealed content is inert rather than merely transparent (theme.tsx:289, 433).
  • The Esc shortcut for cancelling a search is declared with aria-keyshortcuts and defers to open dialogs (Discussion.tsx:277-286, 448).

Language, motion, targets

  • German quotations, citations and the emoji picker are marked lang="de" (theme.tsx:266, 268; ChatBubble.tsx:186).
  • Quotations use <blockquote cite> and <cite>; the photograph uses <figure> and <figcaption>.
  • Reduced motion is honoured throughout, in CSS and in script (see the previous section).
  • Icon buttons are 36 to 40 px or larger; the small text buttons have enough clear space around them to meet 2.5.8 by its spacing exception, as far as the layout classes show.
  • No swipe-only, drag-only or hover-only interaction in the app's own code. The lightbox's swipe-to-dismiss has close-button, backdrop and Esc alternatives (theme.tsx:639-644).

Limitations

This was a static code review. The application was not started, no browser was opened, and no automated tool (Lighthouse, axe) or assistive technology was run. That has consequences:

  • No runtime results are reported. Statements about what a screen reader says, where focus lands on screen, or how a layout renders are inferences from the code and are marked “Requires manual verification” wherever the code alone does not settle them.
  • Contrast ratios are computed from declared colour values, not sampled from pixels. Text over images, gradients and browser-default focus rings were not measured.
  • Layout figures in H2 are arithmetic on the CSS classes. The real rendering may differ.
  • Third-party code was not audited: Cloudflare Turnstile (a remote script and iframe), emoji-mart 5.6.0 (shadow DOM) and yet-another-react-lightbox 3.32.2. Only how the app configures them was reviewed.
  • React Router's default behaviour was established by reading the installed 8.4.0 build in node_modules, not by observing it.
  • Server and data code (auth.server.ts, photo.server.ts, workers/discussions.ts) was read only where it shapes what the user sees.
  • Other files in public/ (discussion-widget.html, discussion-connection-loss.html, discussion-e2ee-and-reporting.html) are standalone documents, not part of the application, and were not audited.
  • The code was being edited during the review. app/app.css and ChatBubble.tsx changed partway through. The animation section was rewritten against the new code and the other references to those files were rechecked, but line numbers will drift as work continues.
  • Content is placeholder in places (profile statistics, “16 people engaged”, local-only reactions). Findings may shift when real data flows through.
  • A static review cannot certify conformance. WCAG conformance needs the manual checks listed above, ideally including testing with disabled users.
