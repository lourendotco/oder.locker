1. The pieces

FileRole

workers/discussions.tsThe Discussions Durable Object: matching, timers, extension votes, and every call to the SFU.

Three parties are involved in a conversation, and it helps to keep them apart:

  • The browser owns the microphone and one RTCPeerConnection.
  • The Durable Object is the only thing that knows who is talking to whom and when it ends. It never touches audio.
  • The SFU (selective forwarding unit) receives each participant's audio and forwards it to the others. It knows nothing about users, conversations or timers.

Browsers never connect to each other. Each one has a single media connection to Cloudflare, and a single WebSocket to the Durable Object for everything else.

2. Is the audio encrypted?

Yes in transit, automatically. No, not end to end. Nothing in our code turns encryption on or off; the first part comes with WebRTC and the second part would have to be built.

LegProtectionWho can read it
Audio, browser ↔ SFUDTLS-SRTP. WebRTC makes this mandatory: a browser will not send unencrypted media, and there is no option to disable it.The two ends of that leg: the browser and Cloudflare's SFU.
Audio, inside the SFUThe SFU decrypts what it receives and re-encrypts it separately for each listener. Each leg has its own keys.Cloudflare, technically. This is what "not end to end" means.
Signalling, browser ↔ workerThe WebSocket is wss:// in production (TLS). In local dev it is plain ws:// on localhost.The browser and our worker.
Worker ↔ SFU APIHTTPS, authorised with the app secret.Our worker and Cloudflare.
What this means in practice
  • Nobody on the network path (Wi-Fi operator, ISP) can listen in.
  • Participants never learn each other's IP address, because they only ever connect to Cloudflare. A peer-to-peer call would expose it.
  • Cloudflare, as the operator of the SFU, is in a position to access the audio. We do not record anything, and nothing in our code asks the SFU to record or to send audio anywhere else.
  • Our own worker never sees audio at all, only the SDP text used to set the connection up.

True end-to-end encryption on top of an SFU is possible. It means encrypting each audio frame in the browser before WebRTC sends it (Encoded Transforms / "insertable streams", usually with the SFrame format), and getting a shared key to the participants without the server seeing it. None of that is implemented. If the privacy policy says anything about calls, it should say "encrypted in transit", not "end-to-end encrypted".

3. Life of one widget

The steps from a click to the end of a conversation, for the second of two people to arrive.

  1. Browser
    The user clicks the microphone. start() appends a <Discussion> to the feed and marks a discussion as running, which disables both entry points.
  2. Browser
    getUserMedia({ audio: true }). If refused, the widget is over ("The microphone can't be used").
  3. Browser
    Opens wss://…/discuss. The session cookie goes with it.
  4. Worker
    Checks Origin, resolves the cookie to a user, forwards the upgrade to the Durable Object with the user in an x-user header.
  5. Object
    Finds someone already waiting, creates a conversation ending in 3:00, and sends both a state message. (With nobody waiting it would send waiting and set a 60 s alarm.)
  6. Browser
    On the first state: creates the peer connection, adds the microphone as a send-only transceiver, makes an offer, sends publish with the SDP.
  7. Object
    Calls the SFU: POST /sessions/new, then POST /sessions/{id}/tracks/new with the offer.
  8. SFU
    Returns a session id and an SDP answer.
  9. Object
    Stores the session id on the socket and sends published with the answer.
  10. Browser
    Applies the answer. ICE and DTLS run; the connection state reaches connected. Sends connected.
  11. Object
    Marks this participant live and broadcasts a new state.
  12. Browser
    Each browser sees someone live whose audio it does not have yet, and sends pull with their user id.
  13. Object
    Translates user ids to SFU session ids (same conversation only) and calls POST /sessions/{mine}/tracks/new with remote tracks.
  14. SFU
    Returns an SDP offer describing the new incoming audio.
  15. Browser
    Applies the offer, creates an answer, sends answer. The track event fires and an <audio> element starts playing.
  16. Object
    PUT /sessions/{mine}/renegotiate with the answer, then sends ready: the browser may pull again.
  17. Object
    At 3:00 (or later if extended) the alarm fires: sends over and closes the sockets.
  18. Browser
    Closes the peer connection, stops the microphone, shows "The conversation has ended", re-enables the entry points.

4. The React side

How it gets onto the feed

The feed (feed.tsx) is a list of React elements in a jotai atom. useDiscussion() returns { discussing, start }: 

start: () => {
  if (discussing) return;
  setDiscussing(true);
  append(<Discussion key={`discussion-${Date.now()}`} />);
}

discussingAtom is the "has it run its course" flag. It is true from the click until the widget is over, and both buttons are disabled={discussing}. The key is unique per click, so a finished widget stays in the feed as a record and a new one is added below it.

Feed blocks normally wait their turn: a block is active only when every block before it has called finish(). A discussion can last ten minutes, so it calls finish() as soon as it mounts. Voices added during a conversation still type out straight away.

State

The server sends remaining milliseconds, never a timestamp. The browser turns that into a local deadline. This way a device whose clock is wrong still shows the right countdown.

The one big effect

Everything with a lifetime (microphone, WebSocket, peer connection) lives in local variables inside a single useEffect, not in React state. They are not things to render, and keeping them in one closure means one release() function can tear all of it down. Two details:

  • Strict Mode. In development React mounts, unmounts and remounts every component. The gone flag makes the first run abandon itself: if the microphone permission resolves after cleanup, its tracks are stopped at once instead of leaking a live microphone.
  • Message queue. Handling a message can be asynchronous (applying an SDP takes a moment). Messages are chained onto one promise so they are always handled in arrival order: 
    let queue = Promise.resolve();
ws.addEventListener("message", ({ data }) => {
  queue = queue.then(() => (gone ? undefined : receive(JSON.parse(data))))…
});
ws.addEventListener("close", () => queue.then(() => end("error")));
    The close handler waits for the queue too, so an over message that arrived just before the close sets the real reason before the fallback "connection was lost" can.

The buttons need to reach into that closure, which is what the refs hangUp, extend and microphone are for.

Pulling other people's audio

The pull() function is the heart of the client's audio logic:

const pull = () => {
  if (!connected || pulling || !latest) return;
  const ids = latest.participants
    .filter(({ id, live }) => live && id !== latest.you && !pulled.has(id))
    .map(({ id }) => id);
  if (!ids.length) return;
  pulling = true;
  ids.forEach((id) => pulled.add(id));
  say({ type: "pull", ids });
};

It is called whenever something changes that might make a pull possible: a new state, our own connection coming up, or ready after the previous pull. The three guards are: our own connection is up, no other pull is in flight, and there is somebody live we have not asked for yet. This is how a third participant's audio gets added to an existing call without special-casing.

Mute, leave, extend

  • Mute sets track.enabled = false. The connection stays up and sends silence. Nothing is sent to the server, so the others are not told you muted.
  • Leave closes the WebSocket. The server notices the close; there is no "leave" message.
  • Extend appears when remaining ≤ 30 s and !maxed. Clicking sends extend and marks you as agreed immediately, without waiting for the server's confirmation.

5. The WebSocket protocol

All messages are JSON with a type. The types are in app/lib/discussion.ts.

Browser → serverMeaning
publish { sdp, mid }My offer, and which media line carries the microphone.
connectedMy connection to the SFU is up; others may pull me.
pull { ids }I want the microphones of these user ids.
answer { sdp }My answer to the SFU's offer.
extendI agree to one more minute.
Server → browserMeaning
waiting { remaining }Nobody yet. Search time left.
state { you, participants, remaining, maxed, votes }The whole conversation, sent on every change: someone joined, left, went live, voted, or the end moved.
published { sdp }The SFU's answer to publish.
offer { sdp }The SFU's offer after pull.
readyThe answer has reached the SFU; the next pull can go.
audio-failedAn SFU call failed. The conversation continues without (some) audio.
over { reason }none, ended, left, busy or error. The socket closes right after.

state is always the full picture, never a delta. A browser that misses one is corrected by the next. The browser never receives another participant's SFU session id; it asks by user id and the server does the lookup, after checking both are in the same conversation.

6. The Durable Object

A Durable Object is a single-threaded instance with its own storage. That is exactly what matchmaking needs: two people arriving at the same moment are handled one after the other, so they cannot both be told "nobody is waiting". There is one instance for everyone, addressed as env.DISCUSSIONS.getByName("theme").

Getting in: workers/app.ts

  • Origin check. A WebSocket is not subject to CORS, so any website could try to open one to us with the visitor's cookie. Requests whose Origin is not our own get a 403.
  • Authentication. The existing getUser(request) resolves the session cookie. No session, 401.
  • Identity. The user is passed to the object in an x-user header that the worker sets itself, overwriting anything the client sent. The object is not reachable from the internet except through this path.

Where state lives

WhatWhereContents
A "seat"The socket's attachment (serializeAttachment)user, since, conversation (null while waiting), session (SFU), live, over
A conversationctx.storage.kv under conversation:<id>startedAt, endsAt, votes

Nothing is kept in instance variables. The object uses the WebSocket Hibernation API: when no events arrive, Cloudflare can evict it from memory while the sockets stay connected, and wake it for the next message or alarm. Anything in memory would be lost; attachments and storage survive. It also means an idle call costs no compute time.

There is no list of "who is waiting". A waiter is simply a socket whose seat has no conversation.

Matching, on connect

  1. The same user already has a socket → over busy.
  2. Someone is waiting → create a conversation with the one waiting longest.
  3. Otherwise, a conversation with exactly two members that started under 30 s ago → join it.
  4. Otherwise → wait.

A third person joins a conversation whose clock is already running; they get the time that is left, not a fresh three minutes.

One alarm for every timer

A Durable Object has a single alarm. After every change schedule() sets it to the earliest deadline that exists: any waiter's since + 60 s or any conversation's endsAt. When it fires, alarm() dismisses whoever has run out and schedules the next one. Alarms are durable: they fire even if the object was evicted in the meantime.

Extension

  • A vote is only accepted in the last 30 s and while the conversation is under 10 minutes in total. Anything else is ignored, so a tampered client cannot extend early.
  • tally() drops votes from people who have left and extends when every remaining member has voted: endsAt += 60 s, capped at startedAt + 10 min, votes cleared.
  • If one of three leaves while the other two have both agreed, the extension goes through.
  • maxed in state tells the browser there is nothing left to ask for.

Leaving

webSocketClose and webSocketError both end up in left(). If fewer than two members remain, the conversation ends for the one left with reason left; otherwise the others get a new state. The over flag on a seat marks a socket the server itself dismissed, so its eventual close event is not processed a second time.

Abuse limits

The browser is not trusted: anyone can write their own client. And the audio does not travel over the WebSocket, so closing the socket does not stop it. A browser keeps its connection to the SFU for as long as it likes. Cloudflare bills what the SFU sends out (publishing into it is free), so the things to control are how long and how much it sends to each client.

  • The server cuts the media. When a conversation ends, or someone's socket closes, silence() asks the SFU for that session's tracks and force-closes all of them (PUT /sessions/{id}/tracks/close with force: true). The connection may stay up, but nothing is forwarded in either direction. A publish or pull that was in flight when the end came is closed as soon as it returns.
  • One pull per participant. The seat records whose microphone it has asked for. Asking again gets ready and no new track, so a client cannot multiply what is sent to it.
  • Audio only. A publish whose SDP is not exactly one m=audio line is refused, so nobody can publish video.
  • One publish per seat, marked before the SFU is called, so two at the same instant cannot both pass.
  • One seat per account, and every seat needs a signed-in session.

7. The SFU and WebRTC

Sessions and tracks

In Cloudflare's model a session is one peer connection to the SFU and a track is one stream of audio or video in it. A track is identified by the publisher's session id plus a name. Every participant here has one session, publishes one track named mic, and pulls the mic track of each other participant into that same session. So a three-person call is three sessions, each sending one track and receiving two.

The SFU has no notion of rooms. "These three people are in a call" exists only in our Durable Object, which is why it must be the one to decide who may pull what.

Why the server makes the calls

The SFU's HTTPS API (https://rtc.live.cloudflare.com/v1/apps/{appId}/…) is authorised with the app secret. Anyone holding it could pull any track in the app. It therefore stays in the worker, and the browser's SDP is relayed through the WebSocket.

Our messageSFU callDirection of the SDP
publishPOST /sessions/new
POST /sessions/{id}/tracks/new (location local)		Browser offers, SFU answers.
pullPOST /sessions/{id}/tracks/new (location remote)SFU offers.
answerPUT /sessions/{id}/renegotiateBrowser answers.

Note the direction flips. When publishing, the browser knows what it wants to send, so it writes the offer. When pulling, only the SFU knows what the incoming audio looks like, so it writes the offer and the browser answers.

One change at a time

An SDP exchange on a session must finish before the next one starts, or the SFU rejects it. The browser enforces this for its own session with the pulling flag, cleared only by ready, which the server sends after renegotiate has returned. Because each browser is the only source of changes to its own session, the server needs no queues.

Connectivity

  • The peer connection is created with Cloudflare's STUN server (stun.cloudflare.com:3478), which lets the browser discover its public address.
  • After creating the offer the browser waits up to one second for ICE candidates to be gathered, so they are inside the SDP it sends. There is no separate "trickle" of candidates over the WebSocket.
  • bundlePolicy: "max-bundle" puts outgoing and incoming audio on one network transport, so adding a participant does not need a new connection.
  • No TURN server is configured. The SFU is on public addresses, which works from almost all networks; a network that blocks UDP outright would fail to connect.

8. The bug that was fixed

The first version always showed "The audio couldn't connect" on one of two devices, while audio flowed in the other direction. The SFU's error was: 

not_found_track_error: Track not found on remote peer. Make sure the
publisher peer is connected and sending packets for this track

The server announced a participant as available as soon as the SFU had accepted their offer. But at that point their browser had not even received the answer, let alone connected. Whoever published second was announced early, and the first device's pull for them was refused. The second device pulled a moment later, when the first was long connected, so that direction worked.

The fix is the connected message and the live flag: a microphone is announced only when its owner's connection is up, and a browser only pulls once its own connection is up (pulling on an unconnected session gave a different error, transport_unavailable_error).

A side effect worth knowing: the SFU also refuses a pull when the publisher is connected but sending nothing (empty_track_error). A muted microphone still sends silence, so mute is fine.

10. Known gaps

  • A connection that never comes up is silent. If a browser stays in "connecting", it is never announced and nobody hears anything, with no message until the browser gives up (about 30 s), when "The audio couldn't connect" appears. This happened once in testing and was not explained.
  • No retry. A failed pull is reported and not attempted again.
  • The 10-minute cap has not been run in real time. The matching, the 60 s search limit, the 30 s join window, leaving, and one extension were tested against the real object; the cap was only checked by reading the code.
  • No limit on how often one account can discuss. Each conversation is capped at 10 minutes and its audio is cut at the SFU when it ends (section 6), but nothing stops two accounts from starting one conversation after another.
  • Deploys interrupt calls. Deploying restarts the Durable Object and drops every WebSocket. Widgets in progress show "The connection was lost".
  • One object for everyone. It walks all its sockets on each event. Fine for tens or hundreds of concurrent users, not for thousands.
  • No end-to-end encryption, as described in section 2.
  • Others are not told when you mute, and there is no indicator of who is speaking.
